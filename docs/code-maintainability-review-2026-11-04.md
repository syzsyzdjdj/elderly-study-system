# 代码可维护性与 AI 辅助开发痕迹评审

日期：2026-11-04。范围：当前工作目录中的 Vue 前端、Spring Boot 后端、Spark 模块、Android 外壳、CI 和部署脚本。此次仅评审，未修改业务代码。

后续修复已落入本地源码，见 [修复与验证记录](maintainability-fixes-2026-11-04.md)。下文保留修复前的评审基线。

## 结论与边界

整体可维护性主观评估约 6/10：已有可运行项目的分层、迁移、测试和部署基础，但模块之间的一致性、业务不变量和发布可复现性仍有明显欠缺。适合继续迭代的小型项目；多人长期维护前应先偿还下面的技术债。

AI 辅助开发的风格信号较明显，但不能根据源码计算“AI 生成百分比”，也不能据此判定作者身份。普通人工开发同样可能产生这些问题。以下判断针对可观察的工程特征，不是来源鉴定。

静态统计（不含 work、依赖和构建目录）：frontend/src 87 个相关源码文件、11461 行；后端主 Java 源码 185 个文件、12179 行；Spark 主 Java 源码 21 个文件、1613 行。行数仅用于理解规模，不作为质量指标。

本次实际执行：前端 21 项测试全部通过，Vite 生产构建通过。未重新运行后端/Spark 全量测试、未做生产压测、未连接手机。本目录不是 Git 工作树，因此无法结合提交历史评估变更粒度和作者来源。下面的并发问题来自代码路径分析，未在数据库上复现。

## 优先处理的问题

### 1. P1：兑换取消缺少原子状态迁移，存在重复退款风险

位置：backend/src/main/java/com/elderly/service/impl/PrizeService.java:135–158。

handle 先 selectById，判断 PENDING，再退积分/库存，最后 updateById。两个事务可以同时读到 PENDING；用户积分行的更新即使被数据库串行化，也不会重新检查兑换记录状态，因此第二个事务仍可能退款。DONE 与 CANCEL 并发也可能出现状态覆盖。@Transactional 保证单事务原子性，不保证这种先查后改的业务幂等性。

建议：在同一事务内先用 WHERE id=? AND status='PENDING' 的条件更新抢占状态，并校验影响行数为 1，再执行退款；或锁定兑换记录后读取。增加双 CANCEL、DONE/CANCEL 并发回归测试。

### 2. P1：奖品价格缺少后端非负校验

位置：backend/src/main/java/com/elderly/controller/PrizeController.java:67；service/impl/PrizeService.java:55；mapper/SysUserMapper.java 的 deductPoints。

管理保存接口直接接收实体，仅补默认值；实体无非负约束。若管理员提交负 pointsCost，SQL points = points - cost 就会增加用户积分。这个问题以管理员保存了错误价格为前提，不是普通用户可直接修改价格。

建议：使用专门保存 DTO，并对价格、库存、状态设定范围；服务层保护核心不变量，数据库增加相应约束。零积分奖品是否允许应明确规定。

### 3. P1：内置问答内容存在语义错误，缺少内容审核边界

位置：backend/src/main/java/com/elderly/service/impl/AiChatServiceImpl.java:101。

扫码支付条目在“收款时”的说明中让用户出示“付款码”，将收款和付款概念混在一起。它是硬编码的本地兜底答案，在未命中 FAQ 且大模型关闭或失败时仍可能发送给老人。代码可正常运行、模型也可以完全关闭，但内容仍会出错。

建议：先人工复核并修正此条；将这类答案迁入可审核、可追溯版本的 FAQ 内容，而不是持续扩充 Java 字符串。测试应覆盖典型提问的实际答案，不只验证请求成功。

### 4. P2：自动分类依赖固定数据库 ID，匹配顺序会压过具体含义

位置：backend/src/main/java/com/elderly/service/impl/CourseServiceImpl.java:161–260。

关键词映射写死 11L、12L、13L 等分类主键，分类维护或重建后容易失配。存在 ID 只能证明记录存在，不能证明语义仍正确。此外，LinkedHashMap 中“微信”先于“微信支付”，匹配到第一个关键词就退出，因此只包含“微信支付”的课程也会先命中社交聊天分类。

建议：用稳定分类编码与可配置规则；明确规则优先级或采用最长关键词匹配；把建议分类与人工确认分开。增加重叠关键词、分类删除重建的测试。

### 5. P2：角色、菜单配置与实际页面访问不一致

位置：frontend/src/router/index.js:55、68；views/admin/AdminLayout.vue:55；views/admin/Roles.vue；后端 CourseController.java:76 等。

前端只允许 admin 访问后台，导航来自固定 ALL_MENUS；角色管理页面却可以分配菜单，后端多个接口允许 COURSE_MANAGER。结果是权限分配界面与实际导航/路由之间缺少闭环。这里是配置和使用体验的不一致，不应直接表述为已经发现越权漏洞。

建议：先明确是否真正支持多个管理角色。支持则由统一权限模型生成路由与菜单，并保持后端鉴权；不支持则简化配置界面，避免提供无实际效果的设置。

### 6. P2：样式采用叠加覆盖方式，修改影响难以预测

位置：frontend/src/main.js 的样式导入顺序；styles.css:309、532；app-theme.css:88、152。

全局 styles.css 为 1092 行，页面 scoped 样式之外又通过 app-theme.css 的 #app 选择器覆盖同名布局。课程卡片、聊天容器等样式散布多个位置，修改一个规则可能被更高优先级的规则覆盖。

建议：公共设计令牌保留全局；公共布局收敛到组件；页面布局在页面维护；迁移时删除旧定义。对登录、首页、学习、问答、后台设置固定视口的截图回归检查。

### 7. P2：测试已有价值，但质量门禁与核心业务风险不匹配

位置：frontend/package.json；frontend/tests；backend/src/test；.github/workflows/ci.yml。

前端现有测试覆盖续签竞态、语音取消和后台时间等实际问题，这点值得保留。但本次未发现奖品兑换/处理的专门后端测试；CI 没有 Android 构建，也未配置 lint/typecheck 或前端端到端流程。测试通过不能证明兑换幂等、角色菜单、摄像头避让等行为正确。源码没有覆盖率门禁，不能据测试数量推算覆盖率。

建议：先补兑换状态机与校验、课程分类、管理角色访问的回归测试；为 Android 增加无生产密钥的编译/lint 任务。之后再逐步引入 ESLint、接口类型和少量关键流程的端到端检查。

### 8. P2：发布流程仍依赖特定旧包与局部 JAR 替换

位置：tools/build_spark_fix.py；deploy/apply-tts-update.py。

脚本有旧包哈希校验、备份和压缩属性保护，比直接覆盖文件更谨慎。但发布依赖 work 中的特定历史 JAR，并替换部分 class/嵌套依赖，最终线上制品不再只是某次统一源码构建的完整输出。连续补丁增加了复现线上状态和交接的成本；断言也不宜承担正式发布中的全部校验。

建议：紧急补丁保留记录，常规发布统一完整制品；为每次发布记录源码版本、构建环境、制品哈希、数据库迁移版本和回滚目标。当前没有 Git 元数据，应先确保正式源码目录具有可追踪版本。

## 后续维护成本

- StudyRecordServiceImpl 在循环内逐条读取课程/用户；CourseServiceImpl 的列表又逐条填分类和收藏状态，存在 N+1 查询。先批量获取，不必为小规模项目立即引入复杂缓存。
- AnalysisServiceImpl 同时维护任务标识列表、显示名称数组、元数据数组和分派逻辑。新增任务需多处同步，建议用有类型的任务定义作为单一来源。
- CourseServiceImpl 持有单线程语音预生成执行器，队列没有显式容量或同课程去重；频繁保存可重复排队。可逐步改为有界队列与版本去重。
- PointService 已有数据库用户行锁，同时还保留不清理的用户/规则锁 Map。先验证并发语义，再决定是否移除重复的进程内锁；不能仅因存在 synchronized 就断言没有数据库并发保护。

## AI 痕迹与真实 AI 能力

较强的风格信号包括：CRUD 和实体模式重复；注释重复描述显而易见的代码；旧注释未随行为更新；后加全局覆盖；用多字段兼容表达式掩盖接口契约不清；以及具体历史版本的一次性补丁持续累积。例如 AiChatServiceImpl 的类注释写“大模型优先”，实际执行却是审核 FAQ 优先；frontend/src/api/course.js 仍保留“若后端未提供该接口”的假设性注释，而接口已经存在。

这些信号更像按需求逐轮补齐后尚未统一整理的项目，也可能来自人工赶工。仅删注释、换命名不会降低维护成本。

反向证据：StudyRecordMapper 用原子 upsert/奖励抢占；AnalysisResultStore 在事务中替换分析结果；推荐服务区分真实与模拟数据并处理冷启动；续签和 TTS 有针对竞态的测试。这些体现了对运行行为的工程处理，不能把项目概括成未经验证的模板。

如果“AI 程度”指业务能力：源码包含可选 DeepSeek 单轮调用、审核 FAQ 和关键词兜底；请求仅包含 system 与当前 user 问题，并未实现对话历史注入。Spark 模块有实际算法实现和评估代码，但效果需要相应数据验证。此次未检查在线配置，不能断言生产正在调用哪种模型，也不能据存在 AI 接口宣称系统具备高级智能体或检索增强能力。

## 建议推进顺序

1. 修复兑换幂等性、价格校验、错误兜底内容，并补对应回归测试。
2. 统一权限与菜单语义；修正固定分类 ID 和重叠关键词匹配。
3. 规范完整制品发布，补 Android CI 与关键页面验收。
4. 按实际变更逐步收敛 CSS、任务元数据和接口 DTO，避免一次性重写整个系统。
